# D02 开发包优化审计

## 范围与结论

本审计针对 `合伙云Pro_D02_大型平台级全量UI重构完整包_V4.0.0_20260817.zip`，SHA-256 为
`B1F26BB0202F176C051EF778C2B61184EB66729FEC90153D2A02B498DA3D084E`。原始包保持不变；
仓库新增的实施层只记录可验证的映射、门禁和缺口。

结论分为两层：

- **视觉交付可用**：包声明 184 个页面、1,153 个状态，且每个状态都有单独 HTML/PNG。
- **生产开发未就绪**：页面中的 `api_groups`、数据库表名和角色文字只是引用清单，不是 OpenAPI、迁移、权限矩阵或第三方支付/实名合同。不能据此声称完整业务可开发或可上线。

## 已优化内容

1. `scripts/audit_d02_package.py` 对 ZIP 执行完整性、Page Index、State Matrix、Page Spec、HTML/PNG、哈希、PNG 尺寸和 Token 引用审计。
2. `design/implementation/D02_DERIVED_TOKENS.json` 补齐 Page Spec 使用但主 Token 文件未声明或未统一命名的四个别名，不改动原始设计包。
3. `design/implementation/D02_IMPLEMENTATION_GATES.yaml` 将视觉、合同、数据、权限、安全与验收拆成明确门禁。

## 已核实问题

### P0：Token 合同不闭合，已建立受控映射

所有 Page Spec 都同时引用 `colors.neutral_50` 和 `color.neutral_50`，并引用主 Token 文件没有声明的
`color.info_100`、`color.error_100`。D02 CSS 确实提供了 `--info-soft` 和 `--error-soft`，因此前述派生 Token
有原始视觉数值依据。未凭空增加其他颜色。

### P0：服务端合同缺失

包内可见 56 个 `api_groups` 和 168 个数据库表名，但没有 OpenAPI/Swagger、数据库迁移、数据 Schema、
权限动作矩阵、支付回调验签协议、对象存储签名上传协议或生产密钥配置。页面规则能够说明“需要什么”，
不能规定“请求和数据如何工作”。

### P1：角色表达不可直接授权

`access.roles` 统计到 84 个中文复合角色字符串，例如“客服/运营/风控/财务按权限”。它们混合职位、
业务前置条件和权限描述，不能直接作为服务端 RBAC 主键。开发前必须转换为稳定的角色 slug、动作、资源、
数据范围和拒绝策略。

### P1：发布波次语义未定义

页面 `release` 字段同时使用 `R01/R10`、`R01-R10`、`P00/R10` 等格式，但包中未声明斜杠与连字符是集合、
依赖还是区间。不能按字符串排序排期，需要先出一份每页唯一归属的发布波次表。

### P1：当前 Android 探索切片不能作为 D02 生产基线

D02 的 Android 实现合同指定 Kotlin、Jetpack Compose 和 Material 3 自定义组件体系；当前仓库中的早期探索代码使用
Java 与 Canvas，并且尚未完成 D02 的逐状态像素差异和真机流程验收。它可作为启动故障的记录，不应继续扩展为正式
客户端；合同齐备后需要按 D02 技术约束重建。

## 开发前最小输入

1. 认证、实名、内容审核、支付/退款/提现、文件上传和管理后台的 OpenAPI 合同与统一错误码。
2. PostgreSQL 或实际选定数据库的 Schema、迁移、金额精度、租户隔离、审计与保留策略。
3. 规范化 RBAC/数据范围矩阵，特别是导出、支付纠正、人工审核和敏感字段访问。
4. 支付服务商、实名服务商、邮件与对象存储的真实接入参数与回调验签规则。
5. 每个 Page ID 的唯一发布波次和依赖关系。

在上述输入没有提供前，只能继续进行视觉组件和无后端依赖的壳层建设；不得伪造登录、付款、实名、审核、
下载校验或权限通过。
